# Пайплайн генерируемых уровней

## Архитектура

```text
request
  -> funGenerateLevel
  -> funValidateGeneratedLevel
  -> funStyleGeneratedLevel
  -> funBuildGeneratedLevel
  -> rGeneratedLevel
```

| Этап | Ответственность |
| --- | --- |
| Catalog | Возвращает упорядоченные пути production Included Files. |
| Provider | Принимает `{ level_path }` и возвращает семантический `level_data` из bundle. |
| Validator | Проверяет обязательные gameplay-инварианты. |
| Styler | Детерминированно преобразует семантику в tiledata. |
| Builder | Создаёт tilemap, коллизии и gameplay instances. |
| Room | Предоставляет слои, камеру, HUD и фон. |

Provider можно заменить процедурным генератором без изменений остальных
этапов. JSON описывает намерение уровня, а не instances или tilemap Room Editor.

## Семантическая модель

Одна клетка равна 12×12 пикселям. Внешний JSON хранит одну редактируемую ASCII
карту `map` размером `width × height`. Непересекающиеся группы символов задают:

- `terrain` — видимая platform-масса и тип поверхности;
- `hazards` — направление шипов;
- `entities` — тип, вариант и mirror gameplay-объекта.

Полный контракт символов находится в `docs/generated-level-format.md`. Codec на
границе ввода разделяет `map` на внутренние `terrain`, `hazards` и `entities`,
чтобы алгоритмы не смешивали ответственности. Наземные entity отображаются в
воздушной клетке над `#`, а decoder восстанавливает их runtime-anchor на строке
ниже.

Runtime validator требует ровно одного player, одну door и оба порога
`star_times`. Остальной input считается доверенным результатом генератора.
Python validator строже: он дополнительно проверяет структуру JSON, геометрию,
опоры и доступность объектов.

## Стилизация

`funStyleGeneratedLevel` возвращает исходный `level_data` и три tiledata-сетки:

```text
platform_tiles  height × width       tsPlatforms, 12 px
grass_tiles     height × width       tsPlatforms, 12 px
spike_tiles     height*2 × width*2   tsSpikesExt, 6 px
```

Координатный hash использует `style.seed` и независимый channel. Результат
воспроизводим и не меняет глобальный RNG.

Для platform topology заполненными считаются `#` и `X`. Открытые стороны задают
края, а единственная открытая диагональ внутри массы — внутренний угол. `X`
рисуется тёмным тайлом без collision. Grass детерминированно добавляется к
свободным поверхностям согласно `grass_chance`.

Hazard разворачивается в четыре 6-пиксельные секции: tip, trap, solid, base.
`^ v < >` кодируют центрированную фазу `6 + 12 + 6`, а `U D L R` — выровненную
`12 + 12`. Направление и фаза одинаковых соседних символов образуют один run.

## Runtime builder

Builder меняет размер комнаты на `width*12 × height*12`, заменяет placeholder
tilemap на слоях `Platforms`, `Grass`, `Spikes` и заполняет ненулевые tiledata.

Коллизии полностью выводятся из декодированных semantic-слоёв:

- `#` разворачивается в четыре solid-клетки 6×6;
- hazard выводит 6 px trap и две 6 px solid-секции из направления и фазы;
- solid-клетки объединяются в прямоугольники `oSolid`;
- горизонтальные runs `=` объединяются в `oJumpThru`;
- одинаково направленные hazards объединяются в `oTrap`.

Entities создаются только из декодированной ASCII-карты. Регистр задаёт mirror,
символ — object и фиксированный scale; type-specific anchor offsets применяет
builder.

## Комната и жизненный цикл

`oGeneratedLevelController` первым в `instanceCreationOrder` стилизует данные,
строит комнату и уничтожает себя. Поэтому HUD и камера уже видят player и
berries в своих Create events.

Единый экран выбора показывает обычные и сгенерированные уровни по 10 номеров
на странице. Порядок уровней 11+ задаёт `catalog.json`. Выбор загружает,
валидирует и кэширует `level_data`, затем открывает `rGeneratedLevel`. Restart
повторно строит тот же кэш, а door открывает стандартный экран победы и
сохраняет прогресс и рекорд в общей последовательности уровней.

## Черновик генерации txt-уровня

Генератор `generated_levels/generate_procedural_level.py`, `generated_levels/procedural` работает в несколько этапов:

1. Строит планарный граф основы пещеры из случайно смещённой решётки. Из набора randomized Kruskal-деревьев выбирается связный каркас с умеренным преобладанием горизонтальных рёбер, короткими однонаправленными цепочками и длинным backbone. Для части seed пробуется одно кольцо, но кольцевой вариант используется только после обычных topology/morphology gates.

2. До растеризации ограничивает граф четырьмя независимыми низкочастотными профилями внешнего силуэта. Внешний `X`, связанный с границей внутреннего холста, занимает 22–30%; это guard от крайностей, а не целевая форма.

3. Превращает единый граф в domain-warped signed-distance field. Радиус ветвей и карманов зависит от шума и степени узла. Глубокий камень становится `X`, границы — непрерывной collision-оболочкой `#`; отдельные перегородки, рёбра и полки после carving не добавляются.

4. Независимо измеряет морфологию и player-clearance navigation graph. Hard gates проверяют внешний `X`, охват холста, центральные открытые пролёты, длинные ровные поверхности, связность footprint игрока и отсутствие дальних прямых teleport-сокращений.

5. Без лимита генерирует полные варианты, рано отбрасывает неподходящую топологию и останавливается после трёх вариантов, прошедших hazards, entities и validator. Из них выбирается вариант с лучшей итоговой оценкой.

6. Размещает jump-through только при наличии конкретной пары takeoff → landing. Возможность прыжка проверяется покадрово с настоящими скоростями, параболой и swept-проверкой маски игрока.

7. Шипы заполняют только короткие ниши вдоль существующих поверхностей `#` и не занимают зоны появления игрока и двери. Их tip, trap, solid и base проверяются на точной сетке 6 px. Оба внешних края run окружены `#` или `X` на уровне шипа и ещё на одну клетку в направлении его основания.

8. Для каждой допустимой пары игрока и двери вычисляется собственный player-clearance shortest path. Пара принимается только при горизонтальном разносе, detour ratio не ниже `1.9` и перекрытой прямой видимости; именно этот восстановленный путь задаёт порядок врагов и ягод. Ягода допустима лишь при наличии позиции телепорта в игровых 12 px, где footprint игрока не пересекает породу или шипы и действительно касается ягоды.

При фиксированном seed весь результат полностью воспроизводим.

Запрошенные размеры относятся к готовому JSON. Алгоритм строит внутреннюю карту
на четыре клетки уже и ниже, затем отдельный frame-этап добавляет по две
строки/колонки `X` со всех сторон. В готовом `map` рамка содержит только `X`.

`TopologySettings` управляет плотностью петель, шириной коридоров, диапазоном внешнего `X` и navigation-порогами. Значения по умолчанию создают плотную single-player топологию. Более открытые варианты получают увеличенную плотность петель, более широкие коридоры и ослабленные morphology/topology gates; отдельный pipeline не требуется.

## Настройка процедурной генерации

Основные параметры находятся в `generated_levels/generate_procedural_level.py`:

- `BATCH_LEVEL_COUNT` — число новых уровней за запуск; по умолчанию `3`.
- `LEVEL_WIDTH_RANGE`, `LEVEL_HEIGHT_RANGE` — диапазоны размеров; по умолчанию `70–110` и `40–60`.
- `OUTPUT_DIRECTORY` — production Included Files в `RandomForest/datafiles/challenge_levels`.
- `LEVEL_TOPOLOGY` — набор настроек формы и критериев отбора уровня.

Каждый запуск продолжает нумерацию после максимального существующего файла и
никогда не перезаписывает номерные JSON. После батча обновляются `catalog.json`
и Included Files в `RandomForest.yyp`. `generated_levels/levels` не изменяется.
Пороги звёзд вычисляются отдельным модулем и сохраняются в `star_times`.

Параметры `TopologySettings`:

- `loop_density` — вероятность попробовать одно осмысленное кольцо; по умолчанию `0.25`.
- `corridor_width_scale` — ширина проходов: больше значение — шире коридоры и комнаты.
- `min_route_detour_ratio` — минимальная извилистость основного маршрута; повышение отбрасывает более прямые уровни.
- `min_endpoint_detour_ratio` — минимальная извилистость пути от игрока до двери.
- `require_endpoint_occlusion` — при `True` игрок и дверь не должны видеть друг друга напрямую.
- `min_horizontal_surface_ratio` — минимальная доля горизонтальных поверхностей относительно стен.
- `max_long_route_sightline_ratio` — допустимая доля дальних прямых сокращений; меньше значение — строже отбор.
- `min_air_ratio`, `max_air_ratio` — допустимый диапазон доли свободного пространства.
- `min_external_rock_ratio`, `max_external_rock_ratio` — допустимый диапазон внешней породы `X`.
- `valid_candidate_target` — количество валидных вариантов для сравнения; генератор работает без лимита попыток, пока не соберёт указанное число. Большее значение обычно улучшает выбор, но замедляет генерацию.

Количество существ настраивается в `generated_levels/procedural/config.py`. Для стандартного уровня 82×47 базовые значения увеличены примерно в полтора раза:

- `REFERENCE_BERRIES = 12` — ягодки.
- `REFERENCE_ENEMIES = 11` — суммарное количество врагов.
- `ENEMY_WEIGHTS` — вероятности предпочтительного типа: 60% слаймов, 25% скелетов и 15% бунгало. Если выбранный тип не помещается, генератор пробует остальные типы.

Количество масштабируется по площади внутренней карты: `base × (area / (78×43))^exponent`, затем результат округляется и ограничивается минимумом. Ягоды распределяются по реальным navigation-distance и могут отклоняться от `base` на две, чтобы покрыть удалённые ветви без тесных кластеров. `BERRY_GROWTH_EXPONENT = 0.65` управляет ростом числа ягод, `ENEMY_GROWTH_EXPONENT = 0.55` — общего числа врагов; значения меньше `1` дают сублинейный рост, чтобы большие уровни не становились перегруженными. Минимумы задаются через `MIN_BERRIES` и `MIN_ENEMIES`. Для карты 500×300 базовые значения составляют 140 ягод и 88 врагов.

Для более открытого уровня увеличьте `loop_density` и `corridor_width_scale`, расширьте диапазоны `air_ratio` и `external_rock_ratio`, снизьте минимальные пороги и повысьте максимальные. Пороговые настройки только фильтруют кандидатов: при строгих значениях поиск может выполняться долго, но не прекращается из-за количества неудачных попыток.

Запуск:

```bash
python3 generated_levels/generate_procedural_level.py
```

Во время работы скрипт одной строкой показывает номер уровня и батча, номер попытки, текущий этап, число найденных кандидатов, причины отказов и прошедшее время. `Ctrl+C` сохраняет уже завершённые уровни и синхронизирует каталог. На очень больших картах одна попытка может занимать минуты: алгоритм построения и критерии качества намеренно не упрощаются.

Поле `style.grass_chance` в готовом JSON меняет густоту травы, но не геометрию уровня.
